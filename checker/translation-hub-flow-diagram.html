Today Per-region isolated translation pipeline
Each region operates independently. Translations are uploaded via XLS to each region separately. No shared infrastructure.
⚠ Pain points (Management-visible)
  • Same 8,000 keys translated separately in each region
  • Translations drift between regions silently
  • MT API costs paid N times for identical source text
  • New region onboarding = months of translator work from scratch
  • New language rollout = N× translator effort
  • No global visibility into coverage or quality
⚙ Operational waste
  • PM in each region triages the same new keys independently
  • Brand terminology ("Checker", "Evaluation") can be translated differently
  • Manual XLS copy between regions is rare and error-prone
  • If a region's DB is lost, no off-site recovery of translations
  • Audit and compliance only visible region-by-region
🛠 Current infrastructure (server team)
  • Existing: one DB per region, N PHP servers per region
  • Existing: filesystem cache at checker-files/l10n/
  • No cross-region connectivity for translations
  • No shared services
  • Each region fully self-contained — by design today
▼ Evolution to Phase v1.5 (HUB read-only consumer) ▼
With HUB · v1.5 Centralized translation library with regional consumers
Translations are produced once on the HUB and distributed to all regions. Regions consume but don't yet publish back (that's v2). Existing per-region runtime is unchanged.
✓ Business benefits (Management-visible)
  • ~80% reduction in translator effort per new language
  • MT spend cut from N× to 1× across the fleet
  • New region onboarding: days instead of months
  • Brand terminology guaranteed consistent globally
  • Global coverage and quality dashboard for leadership
  • HUB doubles as off-site backup of translation data
🔄 What changes operationally
  • One global PM team replaces per-region PM duplication
  • New keys triaged once at HUB, propagated everywhere
  • Per-region admin UI becomes optional (for local exceptions only)
  • Each region keeps own DB + .phpi — runtime untouched
  • Regions can still override locally if needed (v2 feature)
🛠 New infrastructure (server team)
  • HUB application servers — hosts admin UI and API
  • HUB database — canonical translation store (~5 GB)
  • HUB sync agent — runs on each region, polls HUB on schedule (e.g.,every midnight or every weekend)
  • Connectivity — HTTPS from each region to HUB; firewall allowlist
  • HUB-side MT credentials — single provider account replacing N
  • Authentication — region-to-HUB service tokens

📋 What we are asking for
Three concrete decisions to unlock this evolution.
For the Management — approval needed
  • Approve incorporating the Translation Module as the first consumer of the CPN HUB infrastructure
  • Approve transition from per-region PM teams to one global PM team for translations
  • Approve scope: v1.5 (HUB read-only) ships after v1 launch; v2 (bidirectional) deferred to a later cycle
For the server team — infrastructure to plan
  • HUB application server(s) — sized for moderate write load and many read-only consumers
  • HUB database — single instance, ~5 GB initial, ~2× growth/year with audit retention
  • Lightweight sync agent installed in each region (PHP CLI cron job is sufficient)
  • HTTPS connectivity from each region to HUB; firewall rules; service auth tokens
  • One MT provider account at HUB-level (replaces N regional accounts)
  • Backup and DR plan for HUB DB (it now holds the global source of truth)
