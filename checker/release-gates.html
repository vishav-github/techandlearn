Release procedure · effective from the next release

Release Gates

Everything is tested on Testing. Preproduction is partially re-tested. Nothing reaches production before the change is documented and the team is briefed.

01 Purpose

This is the release procedure for Checker: what gets tested where, what has to be ready before an update reaches production, and who signs it off. It is written down so it can be followed exactly and referred to in a ticket.

Updates reach clients only through these gates. A change that has not passed them does not go out — regardless of how small it looks or where it was applied. The documentation and briefing steps apply when a release contains enhancements or behaviour changes; a release made up of bug fixes alone keeps the shorter path, so routine fixes are not delayed.

02 The path a change takes

03 Non-negotiable rules

R1

Everything is tested on Testing first. Enhancements and bug fixes alike pass full QA on master2026 before they move to Preproduction. There is no route to Preproduction that skips this.

R2

Preproduction gets a partial QA before release. Gate 2 covers the enhancements in the release and any fix applied directly on Preproduction. A change made straight on Preproduction is never released untested because it was already there.

R3

No production release before the change is documented and the team is briefed. Both are completed before release approval — not written up afterwards. If either is missing, the release waits.

R4

Clients are emailed once the update is live. The client notice goes out at go-live, describing what changed, so nobody is told about behaviour they cannot yet see and nobody meets a change they were never told about.

R5

A bug-only release may skip the documentation and the briefing — and nothing else. Both QA gates, the confirmed timing, and the go-live client notice still apply. This is the only shortcut in the procedure.

R6

No partial releases. The approved scope ships whole. Nothing is split out at the last minute, and nothing that failed a gate travels with the rest of the release.

R7

Release timing is confirmed in writing, and never falls on a weekend. The release is scheduled only once the deployment owner has confirmed a slot, and no production release happens on Friday, Saturday or Sunday. If no confirmation arrives by the agreed cut-off, the release moves to the next window rather than going ahead unconfirmed.

04 What a bug-only release may skip

The documentation and briefing steps apply when the release contains enhancements or behaviour changes. A release made up of bug fixes alone keeps the shorter path — this is what stops the procedure from adding delay to every general update.

Deciding which column applies

If a user could notice the difference without being told, it is a behaviour change. Wording, alerts, comments, defaults, added or moved controls, and anything that changes an existing workflow take the right-hand column. A fix that restores intended behaviour takes the left.

05 Who signs off at each gate

GateOwnerEvidence required to pass
Gate 1 — Full QA on Testing Product & QA QA report on master2026 covering every enhancement and fix in the release, with no open Critical or High findings.
Gate 2 — Partial QA on Preproduction Product & QA Targeted re-test on Preproduction covering the enhancements and any fix applied directly there, plus a regression check on adjacent screens. Items already cleared at Gate 1 are not re-tested in full.
Gate 3 — Release approval Technical lead, with deployment owner Gates 1 and 2 passed; release scope listed and complete; documentation and briefing done where they apply; timing confirmed in writing.

06 Timing

Two rules govern when a release happens. Both apply to every release, bug-only included.

  • Timing is confirmed in writing before the release is scheduled. The deployment owner confirms the slot; without that confirmation the release does not proceed.
  • No production release on Friday, Saturday or Sunday. Releases happen inside the agreed weekday window, except under the exception path below.

07 Exception path

A production-critical fix may skip the release window, but never the gates. It still needs its QA pass on Preproduction, written approval from the technical lead, and a notice to the team the same day. It ships as a complete release of its own scope — that is not a partial release. The exception is recorded on the ticket with the reason, so exceptions stay visible and rare.
